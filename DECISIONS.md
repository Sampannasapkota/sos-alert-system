# Design Decisions

## Overview

This project implements a backend service for handling SOS alerts generated by GPS/satellite tracking devices during trekking expeditions. The application is built using Spring Boot with a layered architecture consisting of Controller, Service, Repository, and Entity layers. PostgreSQL is used as the relational database, and Docker Compose is used to run both the application and database together.

The primary objective was to build a simple but realistic solution that satisfies the assessment requirements while keeping the code easy to understand and extend.

---

# System Design

The application follows a typical layered architecture.

```
Client
   │
Controller
   │
Service
   │
Repository
   │
PostgreSQL
```

Each layer has a single responsibility.

- Controllers handle HTTP requests and responses.
- Services contain business logic and validations.
- Repositories communicate with the database using Spring Data JPA.
- Entities represent the database model.

When an SOS alert is received, the request first reaches the AlertController. The service validates the request, determines which order currently owns the device using the DeviceAssignment table, performs duplicate detection, creates the alert, and stores it in PostgreSQL.

If this application needed to support hundreds or thousands of simultaneous devices, I would separate alert intake from alert processing using a message queue such as RabbitMQ or Kafka so incoming requests are accepted immediately while background workers process alerts asynchronously.

# Data Model

The main entities are:

- Device
- TrekGroup
- Trekker
- Order
- DeviceAssignment
- Alert

A Device is not directly linked to an Order.

Instead, I introduced the DeviceAssignment entity.

```
Device
      │
DeviceAssignment
      │
Order
      │
TrekGroup
      │
Trekkers
```

I chose this because devices are reusable. The same physical GPS tracker may be assigned to different trekking orders over time.

Using a separate DeviceAssignment table preserves assignment history while allowing future assignments without modifying previous records.

Trekkers belong to a TrekGroup because the assessment states that multiple trekkers may share a single GPS device.

# Deduplication

Satellite devices sometimes retransmit identical SOS messages when connectivity is poor.

I considered alerts from the same device within two minutes to be retransmissions.

When a new SOS arrives, the application searches for another alert from the same device inside this time window.

If one exists, the existing alert is returned instead of creating a new database record.

I selected two minutes because it is long enough to filter retransmissions while still allowing users to intentionally send another SOS shortly afterward if needed.

In a production system this threshold should be configurable rather than hardcoded.

# Concurrency


The repository exposes a method that retrieves an alert using `PESSIMISTIC_WRITE`.

The claim operation is executed inside a transaction.

This ensures that while one transaction is claiming an alert, another transaction must wait until the first transaction completes.

If the alert has already been claimed, the second request receives a conflict response instead of overwriting the existing claim.

This approach relies on the database rather than application memory, making it safe even when multiple application instances are running.

---

# Escalation

Unacknowledged alerts are automatically escalated using Spring Scheduling.

A scheduled task runs periodically and searches for alerts that:

- are still in RECEIVED status
- have existed longer than the configured escalation window

Those alerts are updated to:

```
Status = ESCALATED
EscalatedAt = current timestamp
```

I implemented escalation as a scheduled background process because it is simple and satisfies the assessment requirements without introducing additional infrastructure.

The escalation interval is configurable through application properties.

---

# Validation

Several business rules are validated before data is stored.

Examples include:

- Device must exist.
- Order must exist.
- Device assignment dates cannot overlap.
- Assignment cannot exist outside the order duration.
- Orders that are completed or cancelled cannot receive new assignments.
- SOS alerts require a valid assignment.
- Duplicate alerts are ignored.
- Only claimed alerts may be resolved.

# Future Improvements

If this project were developed further, I would consider:

- JWT authentication
- Role-based coordinator accounts
- SMS and email notifications
- Kafka or RabbitMQ for asynchronous processing
- Redis caching
- Audit logging
- Metrics using Micrometer and Prometheus
- Integration tests for concurrent claiming
- Configurable deduplication and escalation policies

# Problems Encountered

One challenge was determining which order an incoming SOS belongs to when devices are reused.

Initially it seemed simpler to store an Order directly inside the Device entity, but that would lose assignment history and would not support device reuse.

Introducing the DeviceAssignment entity solved this problem and also made timestamp-based order resolution straightforward.

Another challenge was preventing overlapping assignments. This was handled by validating assignment periods before saving new assignments.

---

# Assumptions

During implementation I made the following assumptions because the assessment intentionally leaves some details open:

- One device can only belong to one order at a given point in time.
- Multiple trekkers may share a single device through a TrekGroup.
- Devices always send accurate GPS coordinates.
- Coordinators claim alerts using their name rather than a user account.
- Alerts older than the escalation threshold should automatically become ESCALATED.
- Duplicate alerts are identified using device ID and timestamp only.

These assumptions allowed the solution to remain small while still satisfying the assessment requirements.
